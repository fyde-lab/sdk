# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`fyde-sdk` is a Rust client library (not a binary) for talking to a fyde server. It is one crate in a sibling-project workspace at `../` (alongside `server`, `cli`, and `api-protos`) but is *not* a Cargo workspace member — it's built and versioned standalone. Protobuf/gRPC service definitions consumed by this SDK are published to the Buf Schema Registry as `buf.build/fyde-lab/api` (sourced from `../api-protos`, but `build.rs` fetches the BSR module rather than reading that local checkout) and are compiled at build time; `../server` is the corresponding service implementation.

## Commands

- Build: `cargo build`
- Test: `cargo test` (run a single test with `cargo test <test_name>`)
- Lint: `cargo clippy`
- Format: `cargo fmt`
- The dev environment (rustc/cargo/rustfmt/clippy/rust-analyzer/protoc/buf) is provisioned via `../shell.nix` + `.envrc` (direnv/nix). Rust 1.98+ is required (`wreq`/`wreq-util`'s MSRV). `buf` (on `PATH`) is required for `build.rs` to fetch protos from the BSR — `cargo build` needs network access to `buf.build` as a result — unless `FYDE_PROTO_DIR` points at a local checkout of the protos (e.g. `FYDE_PROTO_DIR=../api-protos cargo build`), which needs neither. Building `tests/` (and so `cargo test`/`cargo clippy --all-targets`) also needs `../server` checked out, since `fyde-server` is a path dev-dependency.

## Architecture

`Client` (`src/lib.rs`) is the SDK entry point: `Client::init(ClientConfig)` opens a lazily-connected gRPC channel to `config.url`, shared by every domain, backed by the local SQLite database `config.storage` selects — `Storage::Disk(path)`, or `Storage::Memory` for a private in-memory database that only lives as long as the `Client` — and wires every domain together (`init` itself is just the setup helpers `install_tracing`/`open_database`/`open_secrets`/`lazy_channel` followed by that wiring). `https://` URLs get TLS (rustls, with Mozilla's bundled webpki root store rather than the OS's, so it behaves the same on Android/iOS); `http://` URLs stay plaintext. It exposes each public domain's `Service` trait object: `documents()`, `users()`, `settings()`, `server_state()`, `scripts()`, `scrapers()`. `ClientConfig` also carries the callbacks FFI callers rely on (`on_log`, `on_document_change`, `on_scraper_progress`, `on_scraper_question`). `src/ffi.rs`'s `FydeClient` wraps `Client` for uniffi (Kotlin/Swift). As more server services are added, they should follow the same pattern: a submodule under `src/domains/`, wired into `Client::init`.

Shared building blocks that aren't a domain live under `src/tools/` (`crate::tools::{log, sandbox, sql, testing}`).

### Documents service (`src/domains/documents/`)

Layered like every domain here, each piece only aware of the layer below it, following the same `mod.rs`/`service.rs` split as `../server`'s domain modules:

- `models.rs` — the domain-specific structs (`Document`, `Metadata`), with no logic beyond field definitions and derives.
- `mod.rs` — re-exports the domain types from `models.rs` and `changelog`'s `ChangelogEvent`/`EventType`, plus the `Service` trait (`upload`/`get`/`list`/`search`/`search_facets`/`update_metadata`/`run_scripts`/`start_sync`/`stop_sync`), the business-level API other code depends on. Trait methods take `&self` (not `&mut self`) so implementations can be shared behind `Arc<dyn Service>`. There is no documents gRPC transport: every server interaction goes through the `changelog` domain.
- `parser/` — the public `ParserService` (`parse_content`/`run_scripts`, re-exported from `lib.rs` with `init_parser`): derives a new document's metadata, then runs the user's enabled classification scripts (`scripts::Service::list_user_scripts`) against it, each in a fresh sandboxed Lua VM (`parser/vm.rs`, see "Lua sandbox" below); `parser/transcript.rs` extracts text from PDFs (`pdf_oxide`) and office files (`office_oxide`).
- `dev.rs` — `DevDocumentsClient`, the plain-file `Service` behind `crate::init_dev_scrapers` (see the scrapers section).
- `service.rs` — `DocumentsClient`, the default `Service` implementation, composing an injected `changelog::Service` (to publish), `parser::Service` (to derive metadata) and `Storage` (local, unencrypted cache). `upload` fails fast without a master key (`changelog::Service::ensure_master_key`), reads the file, rejects it with `ErrorCode::DuplicateDocument` if a document with the same content checksum (SHA-256, `parser::checksum`) is already in the local cache — checked before parsing, so no script runs — then parses it, applies the request's metadata overrides and publishes it as an encrypted `Created` changelog event — it never writes the local cache itself; the document lands there when the sync job consumes that event back (on every device of the account). `start_sync`/`stop_sync` start/stop that job (`changelog::Service::start_consume_job`), invoking `ClientConfig::on_document_change` per event. `get`, `list` and `search` never talk to the server — they read documents the sync job persisted straight out of the injected `Storage`; `list` pages through them oldest-first via `offset`/`limit`. `search(SearchQuery)` is `list` with full-text matching and filters, also local-only: the service validates the query (`ErrorCode::InvalidSearchQuery` for a negative offset, non-positive limit or inverted `created_from`/`created_until`) and splits `text` into alphanumeric terms; `storage_sqlite.rs` turns those into an FTS5 `MATCH` (every term as a quoted prefix, so nothing is parsed as FTS syntax) over the `documents_fts` index, ranked by column-weighted `bm25`, plus `SearchFilters` as SQL `WHERE` clauses (any-of within a field, all-of across fields). `documents_fts` (migration `0014`) is a *contentless* FTS5 table (no second plaintext copy of transcripts), keyed through `documents_fts_rowid_map` since `documents` has no stable integer rowid, and kept in sync by triggers on `documents` — never write to it directly. `search_facets(text, filters)` returns, per filterable field, the values (with counts) carried by the documents `search` would match, so a UI only offers choices — and, once a parent filter is picked, sub-choices — that lead somewhere: the service counts each field with *its own* filter lifted and every other one kept (`DocumentsClient::count_documents_by`), so picking a source narrows the sub-categories/purposes on offer while the other sources stay switchable; `storage_sqlite.rs` only runs the `GROUP BY` (through the same `push_matching` as `search`) and the `created_at` `MIN`/`MAX`. Encryption for document content/metadata happens in `changelog/crypto.rs` (see below), since document writes are changelog events — there is no `documents/crypto.rs`.

### Changelog service (`src/domains/changelog/`)

A crate-private (`pub(crate)`) domain: the fyde server's changelog is a blind relay for opaque, client-encrypted write events — document writes (`Created`/`UpdateMetadata`) and script installations (`ScriptInstalled`). Two domains publish through it — `documents` (uploads, metadata updates, and the sync job) and `scripts` (`install_script`) — and nothing outside the crate sees it except `ChangelogEvent`/`EventType` (from `models.rs`), the payload `ClientConfig::on_document_change` receives, which `documents` and `lib.rs` re-export publicly.

Same layering as documents:

- `models.rs` — the domain-specific structs (`ChangelogEvent`, plus the `EventType` enum), with no logic beyond field definitions and derives.
- `mod.rs` — re-exports the domain types from `models.rs`, plus the `Service` trait: `ensure_master_key`, `send`, `start_consume_job` (takes `self: Arc<Self>` since it spawns the consume loop as a background task, and a boxed `FnMut(ChangelogEvent) + Send` callback so the trait stays object-safe) and `stop_consume_job`.
- `grpc_client.rs` — thin gRPC transport (`GrpcClient`), also `&self`-per-call via cloning the generated client's `Channel`. Generated bindings come from `buf.build/fyde-lab/api`'s `changelog/v1/changelog.proto`, fetched via `buf export` in `build.rs`.
- `crypto.rs` — envelope encryption primitives (AES-256-GCM): generates a fresh per-event DEK, encrypts `{event_type, subject_id, content, metadata}` under it, and wraps the DEK under a KEK derived (via SHA-256) from the account master key kept in the OS credential store under `secrets::MASTER_KEY_SECRET` — `encrypt_event`/`decrypt_event` take a `secrets::Service` to read it, and fail if none has been set yet (i.e. before any account has been created or logged into on this device).
- `storage.rs`/`storage_settings.rs` — `CursorStorage`, persisting the id of the last consumed event, implemented over `settings::Service` by `SettingsCursorStorage`.
- `service.rs` — `ChangelogClient`, the default `Service` implementation. The consume job streams and decrypts every event since the persisted cursor, oldest first, then the live tail, retrying a failed pass; it materializes `Created`/`UpdateMetadata` events into the documents cache (skipping, with a warning, a `Created` document whose checksum matches one already cached — `upload` only catches duplicates already synced, so two unsynced uploads of the same file both get published) and `ScriptInstalled` events into the scripts' `installed_scripts` table, advancing the cursor as it goes, and invokes the callback once per event. Only the process holding an advisory `flock` on a lock file in the OS temp dir writes to local storage; others still consume and call back (`write_lock`).

### Users service (`src/domains/users/`)

Authenticates against the server's users service using the OPAQUE asymmetric password-authenticated key exchange protocol (RFC 9807) instead of sending a password: `password` never leaves this SDK in any form, not even hashed. Layered like `documents`, plus one extra seam:

- `mod.rs` — the `Service` trait: `create`/`login`/`logout`/`change_password` (the OPAQUE exchanges below), plus `set_language`/`get_language` (the user's preferred language for `Client::user_message`) and `role`.
- `grpc_client.rs` — thin gRPC transport (`FydeClient`/`GrpcClient`), generated from `buf.build/fyde-lab/api`'s `users/v1/users.proto`, fetched via `buf export` in `build.rs`. Knows nothing about OPAQUE: every method just carries serialized protocol bytes (`opaque_request`/`opaque_response`/`opaque_upload`) back and forth. `create`/`login` are each a two-round-trip exchange — `start_registration`/`finish_registration`, `start_login`/`finish_login` — because OPAQUE requires a response from the other party before the final message of either exchange can be computed.
- `crypto.rs` — the client side of the OPAQUE exchange, via the `opaque-ke` crate, behind an `OpaqueClient` trait (`start_registration`/`finish_registration`/`start_login`/`finish_login`) analogous to `FydeClient`. `finish_registration`/`finish_login` apply Argon2id as OPAQUE's key-stretching function (KSF) at RFC 9106 §4's "low-memory" recommended parameters (64 MiB, 3 iterations, 4 lanes) — deliberately not the RFC's "high-memory" option (2 GiB), which risks getting OOM-killed on the mobile clients this SDK is meant to eventually back (see the top-level `CLAUDE.md`'s `application/` entry). `create` derives the key that wraps the master key from the OPAQUE *export key* (via HKDF-SHA256), not from `password` directly: the export key is already the output of that same key-stretched, oblivious-PRF-hardened exchange, so hashing it again would add cost without adding security. `FydeCipherSuite` (ristretto255 + 3DH/SHA-512 + Argon2id) must match what the server declares (`../server/CLAUDE.md`'s `tools::opaque` section) — though the `Ksf` type specifically only matters here: key stretching in OPAQUE is a client-only operation, so the server's own `Ksf` type is unused there.
- `service.rs` — `UsersClient`, composing `FydeClient` and `OpaqueClient`. A wrong password is usually detected locally, inside `finish_login`, without a round trip to the server: OPAQUE's envelope can't be opened with the wrong password-derived key, so there's no finalization message to produce, which surfaces as `ErrorCode::InvalidCredentials` rather than the `ErrorCode::Unauthenticated` a server-side rejection would produce. Only one account can be signed in per local database: `create`/`login` fail with `ErrorCode::AlreadyLoggedIn` before contacting the server while a session is open, since nothing in the local cache (documents, changelog cursor, scraper cookies) is partitioned per account. `login` unwraps the master key before persisting anything, and the session token is always persisted last, so a failure partway through never leaves a session that looks open but can't decrypt. `logout` clears local state — `secrets::Service::clear` plus `LocalDatabase::wipe`, both always attempted — whether or not the server's `Logout` RPC succeeds (or answers within `SERVER_LOGOUT_TIMEOUT`): an offline device must never be what leaves the account's keys behind.

### Secrets service (`src/domains/secrets/`)

Keeps the values that would compromise the account if read off the device — the raw master key (`MASTER_KEY_SECRET`) and the session token (`SESSION_TOKEN_SECRET`) — in the OS's native credential store instead of the plaintext SQLite `settings` table. Crate-private on purpose (unlike `settings::Service`, which `Client::settings()` exposes publicly): nothing outside the SDK has any business reading these. Same `get`/`set`/`delete` shape as `settings::Service`, plus `clear` (deletes every key in `ALL_SECRETS` — a new secret must be added there or `logout` leaves it behind) and `is_secure_storage_available` (a read probe of the OS store; never fails).

**Plaintext database fallback.** On a device with no usable OS credential store, the user can explicitly accept keeping the account's secrets (master key *and* session token, since a session can't exist without both) in plaintext in the local database's `insecure_secrets` table (migration `0015`) instead: `set` takes a `SecretLocation` (`SecureStorage`/`Database`) saying where to write, while `get` always reads the OS store first, then the database if the key isn't there or the store fails to answer; `delete`/`clear` remove from both (a failed OS-store delete is only reported if the store still answers). `secrets::init` no longer fails when the OS store can't even be opened (e.g. no D-Bus session) — it just has no `SecureStorage`. Only `users::Service::create(…, allow_insecure_storage)` ever picks `Database`, and only when `is_secure_storage_available()` is false; otherwise it fails with `ErrorCode::SecureStorageUnavailable` before contacting the server (`login` always does, since it has no opt-in). `FydeClient::save_new_session` always writes to `SecureStorage`.

- `service.rs` — `SecretsClient` over an injected secure `Option<Storage>` (`None` if the OS store couldn't be opened) and a database `Storage`.
- `storage_sqlite.rs` — the `insecure_secrets` table adapter.

- `storage_keystore.rs` — the real adapter, on `keyring-core` plus each platform's own store crate (target-specific dependencies in `Cargo.toml`): the login Keychain on macOS, the data-protection Keychain on iOS, the Credential Manager on Windows, an Android Keystore-backed vault on Android, and the freedesktop Secret Service over D-Bus on Linux/other desktop Unixes (a headless Linux box with no Secret Service fails rather than silently falling back to plaintext). Entries are namespaced per local database (`fyde-sdk.<sha256 of its canonical path>`), so two `Client`s on two databases never share secrets. **Android apps must hand the library their JNI context once at startup**, before the first `Client::init`: declare a Kotlin class `io.crates.keyring.Keyring` with a companion `external fun initializeNdkContext(context: Context)` and call it from the main activity's `onCreate` — the symbol (`Java_io_crates_keyring_Keyring_00024Companion_initializeNdkContext`) is exported from this crate's own shared library by `android-native-keyring-store`, so no separate `.so` needs loading. Only the Linux path has been exercised while writing this; the other platforms follow each store crate's own documented usage.
- `storage_memory.rs` — process memory only, used for `Storage::Memory` clients so they never touch the OS store.
- `crate::use_in_process_keystore_for_tests` (`#[doc(hidden)]`) swaps the process-wide store for `keyring-core`'s in-memory mock, for `tests/` suites that use `Storage::Disk` (e.g. `reconnect_lifecycle_test.rs`) and must not depend on, or leave entries in, the machine's real keychain.

### Scripts service (`src/domains/scripts/`)

Scripts are Lua programs stored on the server — `ScriptType::Parser` (classification scripts run on every upload by `documents::parser`) or `ScriptType::Scraper` (run by `scrapers`). The public `Service` covers the server's script CRUD (`create_script`/`fetch_script`/`update_script`), per-user enabling (`enable_script`/`disable_script`/`list_user_scripts`/`list_public_scripts`), and installations: `install_script` checks required parameters and publishes the script plus its parameter values as an encrypted `ScriptInstalled` changelog event, so installations sync across the account's devices; `list_installed_scripts`/`fetch_installed_script` read them back from the local `installed_scripts` table the changelog job materializes them into, never from the server. `grpc_client.rs` takes a `ScriptDraft` (every field a script is created/updated with, named) rather than positional arguments; the public trait keeps positional ones since `../scripts` calls it. `InMemoryScriptStorage` is a public, server-less `Service` for tooling that runs parser scripts locally through `init_parser`.

### Settings, sessions and server state (`src/domains/{settings,sessions,server_state}/`)

- `settings` — public key/value `get`/`set`/`delete` over the SQLite `settings` table, for non-secret local state (the changelog cursor, the user's language and role). Secrets go to `secrets` instead.
- `sessions` — crate-private: `authenticated_request` builds a tonic request carrying the session token persisted in `secrets` as a `Bearer` `authorization` header; every domain's `grpc_client.rs` goes through it. `is_connected` is what `Client::init` checks to restart the sync job for a session left open by a previous run.
- `server_state` — public `is_server_reachable`, over the standard gRPC health checking protocol rather than anything in `api-protos`; never fails, reporting a transport failure as `Ok(false)`.

### Scrapers service (`src/domains/scrapers/`)

Runs Lua scraper scripts that log into third-party sites (not the fyde server) and pull documents out of them — ported from the standalone `demo-rust-fyde` CLI (`mlua`-embedded Lua VM, `wreq` for a real Chrome TLS/HTTP2 fingerprint) into this SDK's domain shape. A script loaded here must follow the exact contract `demo-rust-fyde` used: return a table with a single `run(parameters)` function, calling only into a `fyde` global table — `fyde.http.get/post_form/download/set_cookie` (`set_cookie(url, set_cookie)` plants a cookie in the run's jar, for sites that set one from inline JS — a manual `Cookie` header can't stand in for it, since `wreq` skips the jar for a request that already carries one), `fyde.html.select`, `fyde.json.decode/encode`, `fyde.log.*`, `fyde.progress.step/update`, `fyde.input.ask`, `fyde.save_document`, `fyde.session`, `fyde.browser:open/wait_for/fill/click/download` — there is no raw `io`/`os`/socket access from script code. The existing `didaxis.lua`/`impots.lua` scripts run unmodified against this host.

- `mod.rs` — the `Service` trait (`run(name, script, parameters)`, plus `run_installed(&InstalledScript)`, which runs an installed script with its installed parameters and allowed domains under its id, `wreq_emulation`/`follow_redirects` defaulting to `true` since a published script doesn't carry its manifest's flags — the FFI's `run_installed_script` pairs it with `scripts::Service::fetch_installed_script`, and `FydeClient::init`'s `scraper_listener` callback interface carries `on_scraper_progress`/`on_scraper_question` to Kotlin/Swift), object-safe so it can be shared behind `Arc<dyn Service>` like every other domain here.
- `service.rs` — `ScrapersClient`. `mlua::Lua` isn't `Send` (no `send` feature — see Cargo.toml), so unlike every other domain's async code, `run` spawns the whole Lua VM onto a blocking thread (`tokio::task::spawn_blocking`) and builds `Lua::new()` *inside* that closure, never moving an existing instance across threads; a captured `tokio::runtime::Handle` is threaded through so the VM's host functions (`http.rs`, `documents.rs`) can still drive async calls (`Handle::block_on`) from that one blocking thread. Also builds a fresh `browser::init()` per run, the same way — see `browser/` below. Loads this scraper's saved session/cookies before running and persists their final state back before propagating the script's own result: `fyde.session`'s contents are saved whether `run` succeeded or failed (so state from a partial run isn't lost), but cookies (the `fyde.http` jar merged with the browser's) are saved only on success — a failed run saves an empty jar, deleting them. Saved cookies are loaded into both `fyde.http` and the `fyde.browser` webview at startup.
- `host/` — the Rust-to-Lua bridge, one submodule per `fyde.<name>` sub-table, wired together by `host::install`: `http.rs` (owns the `wreq` client/cookie jar and the `build_jar`/`export_cookies` helpers `service.rs` uses around a run), `html.rs`, `json.rs`, `log.rs` (forwards to this crate's `tracing` subscriber, so it already flows through `ClientConfig::on_log` — no separate callback needed), `progress.rs`/`input.rs` (forward to `ClientConfig::on_scraper_progress`/`on_scraper_question` instead of printing to stdout/blocking on stdin like `demo-rust-fyde`, so the consuming application renders its own progress bar and asks questions on screen), `documents.rs` (`fyde.save_document` writes to a scratch temp file and uploads it through `documents::Service::upload`, instead of a plain local file write, so a scraped document ends up synced like any other; an upload rejected as `ErrorCode::DuplicateDocument` is skipped silently rather than failing the script, so re-running a scraper doesn't fail on what it already fetched), `browser.rs` (`fyde.browser`, backed by the `browser` sub-domain below — every method takes an ignored `self` table argument since scripts are meant to call it with colon syntax, `fyde.browser:open(url)`, unlike every other `fyde.*` table's plain dot-call functions). `http.rs` also takes a `debug_http_dump: bool`, threaded in from `Service::run`'s own parameter of the same name (reinstated from `demo-rust-fyde`, which had it on its `Report` type) — when true, `fyde.http.get`/`post_form` additionally record the raw response body in the per-run debug report's `http_request` entries, on top of the method/url/status/timing always recorded; request headers, form values and any request/download body are never recorded, dump or not, since those routinely carry credentials/session cookies.
- `reports/` — a private sub-domain saving each run's debug report: `reports::Recorder` collects the entries the host tables write (`http_request`, `error`, progress, ...), and `service.rs` saves it once the script's `run` returns, through the same `File`/`Sqlite` storage split as `session`/`cookies` below.
- `session/`, `cookies/` — two private sub-domains (same `pub(super)`-trait pattern as `documents::changelog`), keyed by scraper name. Split in two because they're independent concerns: `session` persists the arbitrary JSON object a script reads/writes as `fyde.session`; `cookies` persists the cookie jar `fyde.http` picked up. `demo-rust-fyde` bundled both into one `host/session.rs`/one JSON file. Each exposes its own `StorageConfig` enum (`File(PathBuf)`/`Sqlite(SqlitePool)`) so its `init` can be built on either a `storage_sqlite::SqliteStorage` (the `scraper_sessions`/`scraper_cookies` tables, used by a full `Client`) or a `storage_file::FileStorage` (one JSON file per scraper, used by `init_dev_scrapers` below) — `scrapers::mod.rs` has its own `StorageConfig` of the same shape, which `scrapers::init` fans out into both sub-domains' configs.
- `browser/` — a third private sub-domain, but unlike `session`/`cookies` it has no storage backend of its own: `browser::init()` builds a fresh `driver::BrowserDriver` per scraper run (from `service.rs`, not from `scrapers::init`), giving a scraper script a real, embedded webview (`wry`, windowed via `tao`) for sites a plain `fyde.http` request can't get past — a client-rendered SPA with no plain-HTML fallback, or a WAF/JS challenge (Datadome, etc.) that only passes when real JS runs (see `../scripts/CLAUDE.md`'s `scaleway`/`boursorama`/`edf` entries for examples of exactly that wall). `BrowserDriver` defers actually creating the window/webview to first use (`ensure_started`) rather than at construction, so a run that never touches `fyde.browser` never needs a display; every real `wry`/`tao` object it creates is `!Send` and never leaves the dedicated OS thread `ensure_started` spawns for it, so every `open`/`wait_for`/`fill`/`click` call crosses onto that thread as an `EventLoopProxy`-delivered `Command`, and (for everything but `open`) blocks on a reply a JS snippet posts back via `window.ipc.postMessage` once it's done — `wait_for`'s polling happens inside the webview's own JS engine, not by Rust re-evaluating anything on a timer. There used to be a `submit` method that submitted a form via an in-page `fetch()` instead of a real click, but that bypassed the page's own submit handling — breaking any bot-mitigation/fingerprinting script hooked onto a real submit event (see `../scripts/CLAUDE.md`'s `ameli` entry) — so it was removed; a script submits a form via `click` on its actual submit control instead. `download(selector, timeout)` clicks `selector` the same way but is for a button/link whose handler triggers the webview engine's own native file-download machinery instead of changing the page — something neither `wait_for` nor `html` can ever observe (confirmed against `cesu.urssaf.fr`'s "Bulletin de salaire" buttons — see `../scripts/scrapers/cesu/script.lua`'s header comment). It's implemented via `wry`'s `with_download_started_handler` (redirects every download to a fresh path under the OS temp dir instead of prompting/using the real downloads directory) and `with_download_completed_handler` (delivers the finished path, or `None` on failure, to the one `download` call waiting on it — there's no map keyed by id here, unlike `PendingReplies`, since nothing calls `download` more than once at a time); the driver reads the file back into memory and deletes it before returning the bytes to Lua. The driver's dedicated thread is torn down via `Drop`, once every `Arc` clone goes out of scope at the end of the run. **Only verified on Linux/WebKitGTK** (`WebViewBuilder::build_gtk`, pairing with `tao`'s GTK main-loop integration — plain `winit` doesn't drive GTK's own main loop, which WebKitGTK needs); macOS/Windows use `wry`'s plain `build()` call instead, per its own docs, but that path has had no real testing here. Its only state carried across runs is cookies, and those go through the `cookies` sub-domain like `fyde.http`'s: `browser::init()` takes the scraper's saved cookies and `set_cookie`s them into the webview as soon as it starts, and `Service::cookies()` reads the webview's back out (filtered to `allowed_domains`; empty, without starting a window, if the run never used `fyde.browser`) for `service.rs`'s `merge_cookies` to fold into the jar it saves — the browser's copy of a cookie wins over `fyde.http`'s. Reading cookies back out of `wry` loses whether each was a domain or host-only cookie (`cookie::Cookie::domain()` strips the leading dot libsoup uses to mark a domain cookie), so every saved cookie is restored as a domain cookie on its saved domain — restoring host-only would drop a site's `Domain=.example.com` SSO cookies for every subdomain and log the next run out (confirmed on bouyguestelecom.fr) — see `driver::to_webview_cookie`, including the double-dot trick its `set_domain` needs. localStorage/IndexedDB are not persisted.

Reaching a `scrapers::Service` normally means going through a full `Client` (which always selects `StorageConfig::Sqlite`), but a scraper script never talks to the fyde server itself (it logs into a third-party site), so `crate::init_dev_scrapers` (`src/lib.rs`) builds one directly: `scrapers::StorageConfig::File(storage_dir)` for `session`/`cookies` instead of the `Client`-managed SQLite pool, plus `documents::init_dev` (`src/domains/documents/dev.rs`)'s `DevDocumentsClient` in place of the real encrypted-upload `documents::Service` — `fyde.save_document` just copies the file to a caller-chosen `out_dir` as plain bytes, the way `demo-rust-fyde` did, instead of publishing a changelog event (there's no account/session to publish one against here). `../scripts` (the repo holding `didaxis.lua`/`impots.lua`) is the one caller of this.

### Layering: simplified hexagonal architecture

Across every domain, the layer boundary is strict: **all business logic — validation, orchestration, cursor/offset bookkeeping, business rules — lives in `service.rs` and nowhere else.** `grpc_client.rs` is a transport adapter: it only sends proto requests and returns raw proto responses, no business rules. `crypto.rs` is a crypto adapter: it only performs envelope encryption/decryption, no business rules. Storage (`SqliteClient`/injected `Storage`) is a persistence adapter: it only reads/writes rows, no business rules. If you find yourself validating input or making a business decision inside a transport, crypto, or storage file, move it into `service.rs`.

### Testing: `service.rs` tests use `mockall`, not real implementations

**`service.rs` business logic (`DocumentsClient`, `ChangelogClient`, `UsersClient`, `SettingsClient`, `ScrapersClient`) must be tested only against `mockall`-generated mocks of its injected dependency traits — `documents::Storage`, `changelog::CursorStorage`, `settings::Service`, `documents::Service`/`changelog::Service` where used cross-domain (this now also includes `scrapers::service` mocking `documents::Service` to test `fyde.save_document` without a real upload, and `scrapers::host::browser` mocking `scrapers::browser::Service` to test `fyde.browser` without a real webview), `scrapers::session::Service`, `scrapers::cookies::Service`, `users::grpc_client::FydeClient`, `users::crypto::OpaqueClient`, `secrets::Service`, etc. — never against a real `grpc_client.rs`, `crypto.rs`, or `SqliteClient`/`SqliteStorage` implementation.** `users::crypto::OpaqueClient` exists specifically so `UsersClient`'s tests never pay the cost of OPAQUE's real (deliberately expensive) key-stretching function, or need to hand-construct protocol-valid response bytes — `crypto.rs`'s own tests (a fixture-only helper, not a mock) are what exercises `DefaultOpaqueClient` for real. Mark each dependency trait `#[async_trait]` plus `#[cfg_attr(test, mockall::automock)]` (this includes traits that were previously written with a bare `-> impl Future<Output = T> + Send` return instead of `async fn` — `automock` needs the `async fn` form, so convert the trait, not just add the attribute), and build the service under test from the generated `Mock*` type. **Configure each test's `Mock*` directly in that test** — `.expect_method().withf(...)...returning(...)` for exactly the calls that test's scenario makes — rather than funneling every test through one shared "fake storage" builder function; a call the test doesn't expect (an `expect_*` that's never set up) correctly panics instead of silently succeeding against a generic backing store, which is often the assertion itself (e.g. "never caches a document for a non-`Created` event" needs no `expect_save_document()` at all). Reach for a small `Arc<Mutex<_>>` capture cell inlined in one test, not a reusable builder, only when that test must read back a value the code under test generates itself (e.g. `users::service`'s `create_persists_an_encrypted_master_key_in_the_credential_store` capturing what `.set()` was called with, since the encrypted master key isn't known ahead of time). Exceptions, whose own tests correctly exercise a real adapter — never do this in `service.rs`: `grpc_client.rs`/`crypto.rs` (real transport/crypto), `src/tools/sql/sqlite.rs` and every domain's own `storage_sqlite.rs` (real SQLite), `secrets/storage_keystore.rs` (real `keyring-core` calls, against its in-memory mock store rather than the machine's keychain), and `changelog/storage_settings.rs` (its own `CursorStorage`-over-`settings::Service` logic, mocking `settings::Service` rather than touching SQLite). One further exception: `changelog::Service`'s `start_consume_job` takes `Box<dyn FnMut(ChangelogEvent) + Send>`, which `mockall` cannot `automock` — code that needs to fake `changelog::Service` (e.g. `documents::service`'s and `scripts::service`'s `RecordingChangelog`) uses a hand-written fake instead, which is legitimate specifically because automocking is impossible there, not a pattern to reach for elsewhere.

### Testing: `Fake*` builders for fixture data

Every domain struct in a `models.rs` that isn't itself a request/input type passed into a `Service` trait method (i.e. every entity a domain returns rather than takes as a parameter — `Document`, `Metadata`, `ChangelogEvent`, `User`) has a matching `Fake*` builder in the same file, behind `#[cfg(test)]`: `FakeDocument`, `FakeMetadata`, `FakeChangelogEvent`, `FakeUser`. Note `Metadata` gets one too even though `changelog::Service::send` also takes it as a parameter — what decides this is whether the struct is part of a *result* type (`Metadata` is a field of `Document`), not whether it happens to also appear as a parameter somewhere. `FakeX::new()` fills every field with random-but-plausible data (via `src/tools/testing/mod.rs`'s primitives — `random_bytes`, `random_hex`, `random_word`, `random_username`, `random_past_timestamp`, all backed by `Uuid::new_v4()` rather than a dedicated `rand` dependency, even though `rand` is already a regular dependency here — keeps every `Fake*` builder's randomness source consistent with `../server`'s), `.with_<field>(value)` overrides one field at a time, and `.build()` consumes the builder into the real struct. A builder can also expose a convenience method beyond the mechanical `with_*` set when it captures a common test need, e.g. `FakeChangelogEvent::for_document(&Document)` sets `document_id` from an existing fixture document instead of making the caller copy the id by hand. Use these instead of hand-writing struct literals in new tests. `Fake*` types and their builder methods are `pub(crate)`, re-exported from `mod.rs` only when another domain's tests need them (e.g. `documents::{FakeDocument, FakeMetadata}` used by `changelog/models.rs`); don't export one pre-emptively before something outside its own file needs it, since an unused `pub(crate) use` fails the crate's clean-clippy bar.

### Testing: `tests/` end-to-end suites must run serially, never in parallel

Every test file under `tests/` (`document_lifecycle_test.rs`, `session_lifecycle_test.rs`, ...) spins up its own real `fyde-server` on a dedicated OS thread and drives it through real gRPC, real SQLite (in-memory), and — critically — real OPAQUE crypto, whose Argon2id key-stretching function is deliberately expensive (see `src/domains/users/crypto.rs`'s 64 MiB/3-iteration KSF note) and runs on every `create`/`login` step. Running these suites concurrently piles up that CPU/memory cost across processes and makes `tests/common/mod.rs`'s `wait_for` polling loops (fixed timeouts) flaky under contention, especially on shared/CI runners. **Tests in `tests/` must therefore never be allowed to run in parallel with each other**, and this can't be left to chance: `cargo test` happens to run separate test binaries sequentially by default, but `cargo nextest` (and any future test added as a second `#[tokio::test]` in the same file) does not.

The enforced solution: every `tests/*_test.rs` top-level test function is annotated `#[serial(e2e)]` from the `serial_test` crate (dev-dependency in `Cargo.toml`). Unlike `--test-threads=1`, `serial_test`'s lock is filesystem-based, so it serializes across separate test binaries too, not just threads within one — meaning the constraint holds regardless of which runner or flags invoke the suite. Any new end-to-end test file added under `tests/` must tag its test function(s) with the same `#[serial(e2e)]` group.

### SQLite client (`src/tools/sql/sqlite.rs`)

`SqliteClient` manages the local database independent of the gRPC services: on disk at the path `Storage::Disk` gives (created on first connect), or in memory for `Storage::Memory`. An in-memory database is named uniquely and opened with a shared cache, and the client holds one keeper connection to it outside the pool: sqlx replaces pooled connections on its own (e.g. after a cancelled query), and with a plain private `:memory:` database the replacement would be a new, empty, unmigrated database. Uses a single-connection pool deliberately, since SQLite only supports one writer at a time. Since it holds every cached document in plaintext, the file is created with mode `0600` on Unix, every connection runs with `PRAGMA secure_delete = ON`, and `wipe` finishes with a `VACUUM`, so nothing deleted on logout can be carved back out of the file. `wipe` lists tables via `pragma_table_list`, skipping FTS5 `shadow` tables (deleting from them directly corrupts the index) and clearing each virtual (FTS5) table last with its `'delete-all'` command — a plain `DELETE` only tombstones FTS5 rows, leaving their tokens readable in the index; any future virtual table must support `'delete-all'` too.

### Lua sandbox (`src/tools/sandbox/`)

Every Lua VM that runs a script — `documents::parser::vm::sandboxed` (server-supplied classification scripts, run on every upload) and `scrapers::service::sandboxed_lua` — is built by `sandbox::new_vm`, never `Lua::new*` directly: it loads only the requested safe `StdLib` subset, strips `dofile`/`loadfile`/`load` from the always-loaded base library, and enforces `sandbox::Limits` — a heap cap (`set_memory_limit`) and a Lua-instruction budget (a global `every_nth_instruction` hook). The budget counts instructions, not wall-clock time, on purpose: a scraper legitimately spends most of its time blocked in host functions (network, `fyde.input.ask`). Scripts must be loaded with `sandbox::load_source`, never `lua.load`: `mlua` otherwise auto-detects precompiled bytecode by its `\x1bLua` signature and runs it unverified, even in safe mode. Parser scripts run on a blocking thread (`spawn_blocking`), like scraper runs. Separately, a scraper's `allowed_domains` fails closed: an empty list allows no host, and an IP-literal host only matches an identical entry, never by suffix.

### Errors

All fallible SDK operations — every public method included — return the crate-wide `Result<T> = Result<T, Error>` (`src/error/mod.rs`, re-exported from `src/lib.rs`). `Error` is a struct carrying three things:

- `code()` — an `ErrorCode`, a public `#[non_exhaustive]` enum with one explicit, stable `u32` value per kind of failure (`1xxx` local device, `2xxx` server/network, `3xxx` account, `4xxx` documents, `5xxx` scripts; displayed as `FYDE-<value>`). Uniqueness is compiler-enforced (`#[repr(u32)]` rejects duplicate discriminants). Never renumber or reuse a released value — callers persist and match on them. The list lives in one `for_each_error_code!` macro that generates both `ErrorCode` and `ffi::FfiError`.
- `original()` / `Display` — the technical error: the crate-private `ErrorKind` enum (gRPC transport/status, UUID parsing, I/O, sqlx, XDG, JSON, encryption, ...) wrapping the third-party error via `thiserror` `#[from]`, prefixed by every context message. For logs only, never for end users.
- `user_message(language)` — short, non-technical wording for end users, from `src/error/messages.rs` (English and French, matching `../application`'s own translations; anything else falls back to English). `Client::user_message(&err)` picks the language the user set via `UsersService::set_language`, falling back to the system language.

Inside the crate, raise failures as an `ErrorKind` (`ErrorKind::DocumentNotFound(id).into()`, or just `?` — `From<ErrorKind>` and `From<each wrapped third-party error>` are implemented for `Error`) and match on `err.kind()` in tests. To add a failure: add an `ErrorKind` variant (if a new cause), map it in `ErrorKind::code`, and if it needs its own code add one to `for_each_error_code!` plus its wording in every language in `messages.rs` — the `match` there is exhaustive, so a missing translation fails to compile. Never introduce per-module error types.

Across the FFI boundary (`src/ffi.rs`), `FfiError` is a *flat* uniffi error with one variant per `ErrorCode` whose message is the localized user wording (so Kotlin gets `FfiException.InvalidCredentials` etc., and `Exception.message` is display-ready); the technical description is logged rather than sent. Every exported `FydeClient` method runs its body through `FydeClient::localized`, which picks the user's language — there is deliberately no `From<Error> for FfiError`, so no path can skip it.

**Every error must be wrapped with a context message before it's returned** — never a bare `?` with no explanation of what was being attempted. Use the crate-wide `ErrorContext` trait (`src/error/mod.rs`) at each fallible site: `.context("failed to open local database")` or `.with_context(|| format!("failed to write changelog offset {offset}"))`. This prepends the message to the error's context list without changing its `ErrorCode`, preserving the original as its `source()`. See `src/tools/sql/sqlite.rs` for examples.
