# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`fyde-sdk` is a Rust client library (not a binary) for talking to a fyde server. It is one crate in a sibling-project workspace at `../` (alongside `server`, `cli`, and `api-protos`) but is *not* a Cargo workspace member — it's built and versioned standalone. Protobuf/gRPC service definitions consumed by this SDK are published to the Buf Schema Registry as `buf.build/fyde-lab/api` (sourced from `../api-protos`, but `build.rs` fetches the BSR module rather than reading that local checkout) and are compiled at build time; `../server` is the corresponding service implementation.

## Commands

- Build: `cargo build`
- Test: `cargo test` (run a single test with `cargo test <test_name>`)
- Lint: `cargo clippy`
- Format: `cargo fmt`
- The dev environment (rustc/cargo/rustfmt/clippy/rust-analyzer/protoc/buf) is provisioned via `../shell.nix` + `.envrc` (direnv/nix). `buf` (on `PATH`) is required for `build.rs` to fetch protos from the BSR — `cargo build` needs network access to `buf.build` as a result.

## Architecture

`Client` (`src/lib.rs`) is the SDK entry point, with two constructors: `Client::connect(url)` opens a gRPC connection backed by the local SQLite database in the default XDG data directory, and `Client::connect_memory(url)` does the same but backed by a private in-memory database that only lives for the process's lifetime. Both expose the same service-specific sub-clients (`documents()` → `&DocumentsClient`). As more server services are added, they should follow the same pattern: a submodule under `src/domains/`, wired into `Client`.

### Documents service (`src/domains/documents/`)

Layered in three pieces, each only aware of the layer below it, following the same `mod.rs`/`service.rs` split as `../server`'s domain modules:

- `models.rs` — the domain-specific structs (`Document`, `Metadata`), with no logic beyond field definitions and derives.
- `mod.rs` — re-exports the domain types from `models.rs` and `changelog/models.rs` (`ChangelogEvent`, `EventType`), plus the `Service` trait (`upload`/`get`/`list`/`update_metadata`/`sync`), the business-level API other code depends on. Trait methods take `&self` (not `&mut self`) so implementations can be shared behind `Arc<dyn Service>`.
- `grpc_client.rs` — thin gRPC transport (`GrpcClient`). Knows nothing about documents semantics; just sends proto requests and returns raw proto responses. Methods take `&self`, cloning the underlying tonic `Channel` per call (cheap, safe to use concurrently) since the generated client's RPC methods require `&mut self`. Generated protobuf bindings are compiled by `build.rs` (via `buf export buf.build/fyde-lab/api` then `tonic-prost-build`) and included with `tonic::include_proto!("documents")`.
- `service.rs` — `DocumentsClient`, the default `Service` implementation, which composes the crypto and gRPC layers and delegates local, unencrypted persistence to an injected `Storage`. `download`/`download_many` are single round-trips against the server: the server's `FetchDocument`/`FetchDocuments` RPCs return `EncryptedDocument`s (ciphertext content, wrapped DEK, and encrypted metadata together), so no separate lookup is needed to decrypt them. `get` and `list`, unlike `download`, never talk to the server — they read documents previously persisted by `save` straight out of the injected `Storage`; `list` pages through them oldest-first via `offset`/`limit`. There is no listing RPC — `ListDocuments` was removed from `documents.proto`, so `list` only ever sees documents already cached locally by a prior `download`/`download_many`. `sync` delegates straight to the internal `changelog::Service::consume`; encryption for document content/metadata now happens in `changelog/crypto.rs` (see below), since document uploads/downloads are folded into changelog events — there is no `documents/crypto.rs`.

### Changelog service (`src/domains/documents/changelog/`)

A private submodule of `documents` — not a sibling domain. Nothing outside `documents` may reference `changelog::Service`, `changelog::init`, or any other changelog item directly (both are scoped `pub(super)`); the only way to reach the changelog from outside `documents` is `documents::Service::sync`, which just calls `changelog::Service::consume`. `ChangelogEvent`/`EventType` (from `changelog/models.rs`) are the one exception — they're the payload `sync` hands back to callers, so `documents::mod.rs` re-exports them publicly.

Same layering as documents:

- `models.rs` — the domain-specific structs (`ChangelogEvent`, plus the `EventType` enum), with no logic beyond field definitions and derives.
- `mod.rs` — re-exports the domain types from `models.rs`, plus the `Service` trait (`send`/`consume`), `&self` for the same `Arc<dyn Service>`-sharing reason as `documents::Service`. `consume` takes a boxed `FnMut(ChangelogEvent) + Send` callback (not a generic parameter) so the trait stays object-safe for `Arc<dyn Service>`.
- `grpc_client.rs` — thin gRPC transport (`GrpcClient`), also `&self`-per-call via cloning the generated client's `Channel`. Generated bindings come from `buf.build/fyde-lab/api`'s `changelog/v1/changelog.proto`, fetched via `buf export` in `build.rs`.
- `crypto.rs` — envelope encryption primitives (AES-256-GCM), the same technique used for document uploads before the documents service was folded into the changelog: generates a fresh per-event DEK, encrypts `{event_type, document_id, content, metadata}` under it, and wraps the DEK under a KEK derived (via SHA-256) from the account master key persisted in the settings store under `users::MASTER_KEY_SETTING` — `encrypt_event`/`decrypt_event` take a `settings::Service` to read it, and fail if none has been set yet (i.e. before any account has been created or logged into on this device).
- `service.rs` — `ChangelogClient`, the default `Service` implementation. `consume` opens a `WatchEvents` subscription and, for every event it receives, pages through `ListEventsSince` starting from the cursor persisted in an injected `Storage`, advancing that cursor after each page; the callback is invoked once per event during both the initial catch-up and the live subscription. `list_since` and the private `catch_up` helper are inherent methods, not part of the trait, since nothing outside `consume` calls them.

### Users service (`src/domains/users/`)

Authenticates against the server's users service using the OPAQUE asymmetric password-authenticated key exchange protocol (RFC 9807) instead of sending a password: `password` never leaves this SDK in any form, not even hashed. Layered like `documents`, plus one extra seam:

- `mod.rs` — the `Service` trait (`create`/`login`/`logout`) — unchanged in shape from before OPAQUE; only what happens inside `service.rs` changed.
- `grpc_client.rs` — thin gRPC transport (`FydeClient`/`GrpcClient`), generated from `buf.build/fyde-lab/api`'s `users/v1/users.proto`, fetched via `buf export` in `build.rs`. Knows nothing about OPAQUE: every method just carries serialized protocol bytes (`opaque_request`/`opaque_response`/`opaque_upload`) back and forth. `create`/`login` are each a two-round-trip exchange — `start_registration`/`finish_registration`, `start_login`/`finish_login` — because OPAQUE requires a response from the other party before the final message of either exchange can be computed.
- `crypto.rs` — the client side of the OPAQUE exchange, via the `opaque-ke` crate, behind an `OpaqueClient` trait (`start_registration`/`finish_registration`/`start_login`/`finish_login`) analogous to `FydeClient`. `finish_registration`/`finish_login` apply Argon2id as OPAQUE's key-stretching function (KSF) at RFC 9106 §4's "low-memory" recommended parameters (64 MiB, 3 iterations, 4 lanes) — deliberately not the RFC's "high-memory" option (2 GiB), which risks getting OOM-killed on the mobile clients this SDK is meant to eventually back (see the top-level `CLAUDE.md`'s `application/` entry). `create` derives the key that wraps the master key from the OPAQUE *export key* (via HKDF-SHA256), not from `password` directly: the export key is already the output of that same key-stretched, oblivious-PRF-hardened exchange, so hashing it again would add cost without adding security. `FydeCipherSuite` (ristretto255 + 3DH/SHA-512 + Argon2id) must match what the server declares (`../server/CLAUDE.md`'s `tools::opaque` section) — though the `Ksf` type specifically only matters here: key stretching in OPAQUE is a client-only operation, so the server's own `Ksf` type is unused there.
- `service.rs` — `UsersClient`, composing `FydeClient` and `OpaqueClient`. A wrong password is usually detected locally, inside `finish_login`, without a round trip to the server: OPAQUE's envelope can't be opened with the wrong password-derived key, so there's no finalization message to produce, which surfaces as [`crate::Error::InvalidCredentials`] rather than the `Grpc`(`UNAUTHENTICATED`) a server-side rejection would produce.

### Scrapers service (`src/domains/scrapers/`)

Runs Lua scraper scripts that log into third-party sites (not the fyde server) and pull documents out of them — ported from the standalone `demo-rust-fyde` CLI (`mlua`-embedded Lua VM, `wreq` for a real Chrome TLS/HTTP2 fingerprint) into this SDK's domain shape. A script loaded here must follow the exact contract `demo-rust-fyde` used: return a table with a single `run(parameters)` function, calling only into a `fyde` global table — `fyde.http.get/post_form/download`, `fyde.html.select`, `fyde.json.decode/encode`, `fyde.log.*`, `fyde.progress.step/update`, `fyde.input.ask`, `fyde.save_document`, `fyde.session` — there is no raw `io`/`os`/socket access from script code. The existing `didaxis.lua`/`impots.lua` scripts run unmodified against this host.

- `mod.rs` — the `Service` trait (`run(name, script, parameters)`), object-safe so it can be shared behind `Arc<dyn Service>` like every other domain here.
- `service.rs` — `ScrapersClient`. `mlua::Lua` isn't `Send` (no `send` feature — see Cargo.toml), so unlike every other domain's async code, `run` spawns the whole Lua VM onto a blocking thread (`tokio::task::spawn_blocking`) and builds `Lua::new()` *inside* that closure, never moving an existing instance across threads; a captured `tokio::runtime::Handle` is threaded through so the VM's host functions (`http.rs`, `documents.rs`) can still drive async calls (`Handle::block_on`) from that one blocking thread. Loads this scraper's saved session/cookies before running and persists their final state back — including every cookie picked up and `fyde.session`'s contents — whether the script's `run` succeeded or failed, so state from a partial run isn't lost, before propagating the script's own result.
- `host/` — the Rust-to-Lua bridge, one submodule per `fyde.<name>` sub-table, wired together by `host::install`: `http.rs` (owns the `wreq` client/cookie jar and the `build_jar`/`export_cookies` helpers `service.rs` uses around a run), `html.rs`, `json.rs`, `log.rs` (forwards to this crate's `tracing` subscriber, so it already flows through `ClientConfig::on_log` — no separate callback needed), `progress.rs`/`input.rs` (forward to `ClientConfig::on_scraper_progress`/`on_scraper_question` instead of printing to stdout/blocking on stdin like `demo-rust-fyde`, so the consuming application renders its own progress bar and asks questions on screen), `documents.rs` (`fyde.save_document` writes to a scratch temp file and uploads it through `documents::Service::upload`, instead of a plain local file write, so a scraped document ends up synced like any other). `http.rs` also takes a `debug_http_dump: bool`, threaded in from `Service::run`'s own parameter of the same name (reinstated from `demo-rust-fyde`, which had it on its `Report` type) — when true, `fyde.http.get`/`post_form` additionally record the raw response body in the per-run debug report's `http_request` entries, on top of the method/url/status/timing always recorded; request headers, form values and any request/download body are never recorded, dump or not, since those routinely carry credentials/session cookies.
- `session/`, `cookies/` — two private sub-domains (same `pub(super)`-trait pattern as `documents::changelog`), keyed by scraper name. Split in two because they're independent concerns: `session` persists the arbitrary JSON object a script reads/writes as `fyde.session`; `cookies` persists the cookie jar `fyde.http` picked up. `demo-rust-fyde` bundled both into one `host/session.rs`/one JSON file. Each exposes its own `StorageConfig` enum (`File(PathBuf)`/`Sqlite(SqlitePool)`) so its `init` can be built on either a `storage_sqlite::SqliteStorage` (the `scraper_sessions`/`scraper_cookies` tables, used by a full `Client`) or a `storage_file::FileStorage` (one JSON file per scraper, used by `init_dev_scrapers` below) — `scrapers::mod.rs` has its own `StorageConfig` of the same shape, which `scrapers::init` fans out into both sub-domains' configs.

Reaching a `scrapers::Service` normally means going through a full `Client` (which always selects `StorageConfig::Sqlite`), but a scraper script never talks to the fyde server itself (it logs into a third-party site), so `crate::init_dev_scrapers` (`src/lib.rs`) builds one directly: `scrapers::StorageConfig::File(storage_dir)` for `session`/`cookies` instead of the `Client`-managed SQLite pool, plus `documents::init_dev` (`src/domains/documents/dev.rs`)'s `DevDocumentsClient` in place of the real encrypted-upload `documents::Service` — `fyde.save_document` just copies the file to a caller-chosen `out_dir` as plain bytes, the way `demo-rust-fyde` did, instead of publishing a changelog event (there's no account/session to publish one against here). `../scripts` (the repo holding `didaxis.lua`/`impots.lua`) is the one caller of this.

### Layering: simplified hexagonal architecture

Across `documents` and `documents::changelog`, the layer boundary is strict: **all business logic — validation, orchestration, cursor/offset bookkeeping, business rules — lives in `service.rs` and nowhere else.** `grpc_client.rs` is a transport adapter: it only sends proto requests and returns raw proto responses, no business rules. `crypto.rs` is a crypto adapter: it only performs envelope encryption/decryption, no business rules. Storage (`SqliteClient`/injected `Storage`) is a persistence adapter: it only reads/writes rows, no business rules. If you find yourself validating input or making a business decision inside a transport, crypto, or storage file, move it into `service.rs`.

### Testing: `service.rs` tests use `mockall`, not real implementations

**`service.rs` business logic (`DocumentsClient`, `ChangelogClient`, `UsersClient`, `SettingsClient`, `ScrapersClient`) must be tested only against `mockall`-generated mocks of its injected dependency traits — `documents::Storage`, `changelog::OffsetStorage`, `settings::Service`, `documents::Service`/`changelog::Service` where used cross-domain (this now also includes `scrapers::service` mocking `documents::Service` to test `fyde.save_document` without a real upload), `scrapers::session::Service`, `scrapers::cookies::Service`, `users::grpc_client::FydeClient`, `users::crypto::OpaqueClient`, etc. — never against a real `grpc_client.rs`, `crypto.rs`, or `SqliteClient`/`SqliteStorage` implementation.** `users::crypto::OpaqueClient` exists specifically so `UsersClient`'s tests never pay the cost of OPAQUE's real (deliberately expensive) key-stretching function, or need to hand-construct protocol-valid response bytes — `crypto.rs`'s own tests (a fixture-only helper, not a mock) are what exercises `DefaultOpaqueClient` for real. Mark each dependency trait `#[async_trait]` plus `#[cfg_attr(test, mockall::automock)]` (this includes traits that were previously written with a bare `-> impl Future<Output = T> + Send` return instead of `async fn` — `automock` needs the `async fn` form, so convert the trait, not just add the attribute), and build the service under test from the generated `Mock*` type. **Configure each test's `Mock*` directly in that test** — `.expect_method().withf(...)...returning(...)` for exactly the calls that test's scenario makes — rather than funneling every test through one shared "fake storage" builder function; a call the test doesn't expect (an `expect_*` that's never set up) correctly panics instead of silently succeeding against a generic backing store, which is often the assertion itself (e.g. "never caches a document for a non-`Created` event" needs no `expect_save_document()` at all). Reach for a small `Arc<Mutex<_>>` capture cell inlined in one test, not a reusable builder, only when that test must read back a value the code under test generates itself (e.g. `users::service`'s `create_persists_an_encrypted_master_key_in_settings` capturing what `.set()` was called with, since the encrypted master key isn't known ahead of time). Exceptions, whose own tests correctly exercise a real adapter — never do this in `service.rs`: `grpc_client.rs`/`crypto.rs` (real transport/crypto), `src/tools/sql/sqlite.rs` and every domain's own `storage_sqlite.rs` (real SQLite), and `changelog/storage_settings.rs` (its own `OffsetStorage`-over-`settings::Service` logic, mocking `settings::Service` rather than touching SQLite). One further exception: `changelog::Service`'s `consume` takes `Box<dyn FnMut(ChangelogEvent) + Send>`, which `mockall` cannot `automock` — code that needs to fake `changelog::Service` (e.g. `documents::service`'s `RecordingChangelog`) uses a hand-written fake instead, which is legitimate specifically because automocking is impossible there, not a pattern to reach for elsewhere.

### Testing: `Fake*` builders for fixture data

Every domain struct in a `models.rs` that isn't itself a request/input type passed into a `Service` trait method (i.e. every entity a domain returns rather than takes as a parameter — `Document`, `Metadata`, `ChangelogEvent`, `User`) has a matching `Fake*` builder in the same file, behind `#[cfg(test)]`: `FakeDocument`, `FakeMetadata`, `FakeChangelogEvent`, `FakeUser`. Note `Metadata` gets one too even though `changelog::Service::send` also takes it as a parameter — what decides this is whether the struct is part of a *result* type (`Metadata` is a field of `Document`), not whether it happens to also appear as a parameter somewhere. `FakeX::new()` fills every field with random-but-plausible data (via `src/testing.rs`'s primitives — `random_bytes`, `random_hex`, `random_word`, `random_username`, `random_past_timestamp`, all backed by `Uuid::new_v4()` rather than a dedicated `rand` dependency, even though `rand` is already a regular dependency here — keeps every `Fake*` builder's randomness source consistent with `../server`'s), `.with_<field>(value)` overrides one field at a time, and `.build()` consumes the builder into the real struct. A builder can also expose a convenience method beyond the mechanical `with_*` set when it captures a common test need, e.g. `FakeChangelogEvent::for_document(&Document)` sets `document_id` from an existing fixture document instead of making the caller copy the id by hand. Use these instead of hand-writing struct literals in new tests. `Fake*` types and their builder methods are `pub(crate)`, re-exported from `mod.rs` only when another domain's tests need them (e.g. `documents::{FakeDocument, FakeMetadata}` used by `changelog/models.rs`); don't export one pre-emptively before something outside its own file needs it, since an unused `pub(crate) use` fails the crate's clean-clippy bar.

### Testing: `tests/` end-to-end suites must run serially, never in parallel

Every test file under `tests/` (`document_lifecycle_test.rs`, `session_lifecycle_test.rs`, ...) spins up its own real `fyde-server` on a dedicated OS thread and drives it through real gRPC, real SQLite (in-memory), and — critically — real OPAQUE crypto, whose Argon2id key-stretching function is deliberately expensive (see `src/domains/users/crypto.rs`'s 64 MiB/3-iteration KSF note) and runs on every `create`/`login` step. Running these suites concurrently piles up that CPU/memory cost across processes and makes `tests/common/mod.rs`'s `wait_for` polling loops (fixed timeouts) flaky under contention, especially on shared/CI runners. **Tests in `tests/` must therefore never be allowed to run in parallel with each other**, and this can't be left to chance: `cargo test` happens to run separate test binaries sequentially by default, but `cargo nextest` (and any future test added as a second `#[tokio::test]` in the same file) does not.

The enforced solution: every `tests/*_test.rs` top-level test function is annotated `#[serial(e2e)]` from the `serial_test` crate (dev-dependency in `Cargo.toml`). Unlike `--test-threads=1`, `serial_test`'s lock is filesystem-based, so it serializes across separate test binaries too, not just threads within one — meaning the constraint holds regardless of which runner or flags invoke the suite. Any new end-to-end test file added under `tests/` must tag its test function(s) with the same `#[serial(e2e)]` group.

### SQLite client (`src/tools/sql/sqlite.rs`)

`SqliteClient` manages a local on-disk database independent of the gRPC services, at `$XDG_DATA_HOME/fyde/fyde.db` (falling back to `~/.local/share/fyde/fyde.db`), created on first connect. Uses a single-connection pool deliberately, since SQLite only supports one writer at a time.

### Errors

All fallible SDK operations return the crate-wide `Result<T> = Result<T, Error>` (`src/lib.rs`). `Error` is a single enum covering every failure domain (gRPC transport/status, UUID parsing, I/O, sqlx, XDG, JSON, encryption) via `thiserror` `#[from]` conversions — add new variants there rather than introducing per-module error types.

**Every error must be wrapped with a context message before it's returned** — never a bare `?` with no explanation of what was being attempted. Use the crate-wide `ErrorContext` trait (`src/lib.rs`) at each fallible site: `.context("failed to open local database")` or `.with_context(|| format!("failed to write changelog offset {offset}"))`. This wraps the error in `Error::Context { message, source }`, preserving the original as `#[source]`. See `src/tools/sql/sqlite.rs` for examples.
